# Testing Guide

Patterns, conventions, and guidance for writing tests in Mankunku.

There are five distinct suites, and they are not interchangeable:

| Suite | Runner | What it covers | Command |
|---|---|---|---|
| Unit + integration | Vitest (Node) | Pure logic (audio algorithms, scoring, music theory, planning) **and** integration behaviour — persistence round-trips, cloud-merge semantics, the recorded-take corpus, and cross-module pipelines, against mocked Supabase and a polyfilled IndexedDB | `npm test` |
| E2E | Playwright | Real-browser user flows on Chromium, Firefox, WebKit | `npm run test:e2e` |
| Deploy | bash | `deploy/app/release.sh`'s invariants, against stubbed `npm`/`pm2`/`curl`/`node` | `npm run test:deploy` |
| OMR | pytest (uv, Python 3.12) | The standalone `omr/` subsystem: ABC parsing, normalisation, validation, the benchmark, the CLI — hermetic, no model downloads | `cd omr && uv run pytest` |
| Backing artifacts | Vitest, but regenerated by hand | The seeded backing engine's committed statistics report and golden event dumps | `npm run backing:report` / `npm run backing:golden` |

CI runs four of them. The `test` job runs `npx vitest run` **and** `npm run test:deploy`; the `e2e` job runs `npx playwright test` in parallel with it, sharded six ways across all three engines; the `omr-test` job runs `ruff` and the hermetic `pytest` whenever `omr/` changes. The OMR suite's real-model tests (`uv run pytest -m omr_integration`) download a 429 MB checkpoint and need Hugging Face access to two gated repositories, so they never run in CI.

There is deliberately **no coverage tooling installed** — `@vitest/coverage-v8` is not a dependency, so `--coverage` will not work without installing it first.

## Setup

Tests use [Vitest](https://vitest.dev/). There is no `vitest.config.ts` — the config lives inside `vite.config.ts`, which imports `defineConfig` from `vitest/config`:

```typescript
test: {
  include: ['tests/unit/**/*.test.ts', 'tests/integration/**/*.test.ts'],
  environment: 'node',
  setupFiles: ['./vitest.setup.ts']
}
```

`$lib` resolves via the `sveltekit()` Vite plugin, so there's no alias block in the test config. `tests/e2e/**` is excluded by omission from `include`, not by an `exclude` rule. `vitest.setup.ts` does exactly one thing: `import 'fake-indexeddb/auto'`, so IndexedDB-backed stores (recordings, tune PDFs) work in Node.

### Running Tests

```bash
# Run all tests (unit + integration)
npm test

# Watch mode
npm run test:watch

# Specific file
npx vitest tests/unit/audio/capture.test.ts

# Deploy-script regression suite
npm run test:deploy

# OMR subsystem (hermetic; add -m omr_integration only with Hugging Face access)
cd omr && uv run pytest && uv run ruff check src tests
```

### Test File Location

Unit tests mirror the source structure under `tests/unit/`, one module per file, in a single level of domain subdirectories (`audio/`, `scoring/`, `music/`, `tunes/`, `tricks/`, `lick-practice/`, `persistence/`, `state/`, …). Integration tests live flat under `tests/integration/` and exercise cross-module pipelines and flows (audio processing, adaptive difficulty, cloud sync). Both trees are collected by the default `vitest run` (`npm test`):

```text
tests/
├── unit/            # ~250 files in 24 domain subdirectories, roughly one per module
│   ├── audio/
│   │   └── capture.test.ts
│   └── scoring/
│       └── note-segmenter.test.ts
├── integration/     # ~40 files, flat
│   ├── audio-processing-pipeline.test.ts
│   └── adaptive-difficulty.test.ts
├── e2e/             # ~57 *.spec.ts + fixtures/ (Playwright only)
├── helpers/         # shared factories: lick-builders, tune-fixtures, cloud-sync-mocks, …
└── fixtures/        # data: backing/ (golden event JSON), leadsheets/, recordings/
```

Shared test data belongs in `tests/helpers/` (builders and mocks) or `tests/fixtures/` (inert data files) — never inlined into a second spec.

## Mocking Audio APIs

Browser audio APIs (`AudioContext`, `AnalyserNode`, `MediaStream`) don't exist in the Node test environment. Use mock factories.

### Mock AudioContext

```typescript
function createMockAudioContext() {
  return {
    createMediaStreamSource: vi.fn(() => ({
      connect: vi.fn(),
      disconnect: vi.fn()
    })),
    createAnalyser: vi.fn(() => createMockAnalyser()),
    sampleRate: 48000,
    currentTime: 0
  };
}
```

### Mock AnalyserNode

```typescript
function createMockAnalyser(fftSize = 4096) {
  const buffer = new Float32Array(fftSize);
  return {
    fftSize,
    smoothingTimeConstant: 0,
    getFloatTimeDomainData: vi.fn((out: Float32Array) => {
      out.set(buffer);
    }),
    connect: vi.fn(),
    disconnect: vi.fn(),
    context: { sampleRate: 48000, currentTime: 0 },
    _buffer: buffer  // exposed for test manipulation
  };
}
```

### Mock MediaStream

```typescript
function createMockStream() {
  const track = { stop: vi.fn(), kind: 'audio' };
  return {
    getTracks: vi.fn(() => [track]),
    _track: track
  };
}
```

### Mock Navigator

```typescript
vi.stubGlobal('navigator', {
  mediaDevices: {
    getUserMedia: vi.fn(async () => mockStream)
  },
  permissions: {
    query: vi.fn()
  }
});
```

## Mocking Module Dependencies

Use `vi.mock()` to mock internal modules before importing the module under test:

```typescript
let mockAudioCtx: ReturnType<typeof createMockAudioContext>;

vi.mock('$lib/audio/audio-context.ts', () => ({
  initAudio: vi.fn(async () => mockAudioCtx)
}));
```

### Reset Between Tests

Audio modules use module-level singletons. Use `vi.resetModules()` in `beforeEach` and re-import:

```typescript
let captureModule: typeof import('$lib/audio/capture.ts');

beforeEach(async () => {
  vi.resetModules();
  mockAudioCtx = createMockAudioContext();
  captureModule = await import('$lib/audio/capture.ts');
});
```

## Testing Patterns

### Pure Function Tests

Most scoring, music theory, and phrase modules are pure functions — test directly without mocks:

```typescript
import { segmentNotes } from '$lib/audio/note-segmenter.ts';

it('uses median MIDI note for robustness', () => {
  const readings = [
    makeReading(60, 0.1),  // C4
    makeReading(60, 0.2),  // C4
    makeReading(61, 0.3),  // C#4 (outlier)
  ];
  const notes = segmentNotes(readings, [0.0], 0.5);
  expect(notes[0].midi).toBe(60);  // median wins
});
```

### Helper Factories

Shared builders live in `tests/helpers/`: `lick-builders.ts` (phrases and licks), `tune-fixtures.ts`, `cloud-sync-mocks.ts` (the in-memory Supabase), `leadsheet-corpus.ts`, and `audio-fixtures.ts` (`loadWavFixture`, `makeFakeAudioBuffer`, `makeSine` — the recorded-take corpus runs through these). Reach for them before writing a local helper like this one:

```typescript
function makeReading(midi: number, time: number): PitchReading {
  return {
    midiFloat: midi,
    midi,
    cents: 0,
    clarity: 0.9,
    time,
    frequency: 440 * Math.pow(2, (midi - 69) / 12)
  };
}
```

### Testing Scoring

```typescript
import { scorePitch } from '$lib/scoring/pitch-scoring.ts';

it('returns 1.0 for correct MIDI note', () => {
  const expected = { pitch: 60, duration: [1, 4], offset: [0, 1] };
  const detected = { midi: 60, cents: 0, onsetTime: 0, duration: 0.5, clarity: 0.9 };
  expect(scorePitch(expected, detected)).toBe(1.1);  // 1.0 + 0.1 intonation bonus
});

it('returns 0.0 for wrong MIDI note', () => {
  const expected = { pitch: 60, duration: [1, 4], offset: [0, 1] };
  const detected = { midi: 62, cents: 0, onsetTime: 0, duration: 0.5, clarity: 0.9 };
  expect(scorePitch(expected, detected)).toBe(0);
});
```

### Testing Proficiency Advancement

```typescript
import { createInitialScaleProficiency, processScaleAttempt } from '$lib/difficulty/adaptive.ts';

it('advances after consistent high scores', () => {
  let state = createInitialScaleProficiency();
  for (let i = 0; i < 11; i++) {
    state = processScaleAttempt(state, 0.90);
  }
  expect(state.level).toBeGreaterThan(1);
});
```

### Testing Validation

```typescript
import { validatePhrase, rulesForDifficulty } from '$lib/phrases/validator.ts';

it('rejects phrases with intervals too large for the level', () => {
  const phrase = makePhraseWithInterval(10);  // 10 semitones
  const rules = rulesForDifficulty(1);        // max 5 semitones
  const result = validatePhrase(phrase, rules);
  expect(result.valid).toBe(false);
});
```

## E2E tests (Playwright)

Everything a Node test cannot reach: navigation, hydration, real DOM, persistence
round-trips through a real browser. Config is `playwright.config.ts` — `testDir:
'tests/e2e'`, three projects (`chromium`, `firefox`, `webkit`), `fullyParallel`,
2 retries and 2 workers in CI, 0 retries locally. The `webServer` block runs
`npm run build && npm run preview -- --port 4173` with `PLAYWRIGHT=1` in its env,
which is what activates the `e2e-test-user` cookie branch in `src/hooks.server.ts`.

```bash
npm run test:e2e                    # all three browsers
npm run test:e2e:ui                 # interactive runner
npm run test:e2e:debug              # inspector
npm run test:e2e:report             # open the last HTML report
npx playwright test tests/e2e/lick-practice-session.spec.ts --project=chromium
```

Running beside another checkout, set `PLAYWRIGHT_PORT` (for example
`PLAYWRIGHT_PORT=4273 npx playwright test`): locally Playwright reuses whatever
server already holds the port, so a worktree run can otherwise test another
checkout's build without any error.

Two rules the suite enforces on itself:

- **Import from the local fixture, never `@playwright/test`.** Anonymous specs import
  `{ test, expect }` from `tests/e2e/fixtures/test.ts`; signed-in specs import from
  `fixtures/auth.ts`, which extends it. Both carry an **automatic** console guard:
  every test fails on an unexpected `console.error` or `pageerror`, whether or not
  it names the `consoleCollector` fixture. A spec whose subject is a 404 page opts in
  with `test.use({ allowDocument404: true })`, which admits only that document's own
  404 line. Genuinely-expected noise goes in `IGNORED_PATTERNS` in
  `fixtures/console-errors.ts`, with a comment naming the spec and engine.
- **Audio and auth are mocked, not real.** `fixtures/audio.ts` replaces
  `MediaRecorder` + `getUserMedia`; `fixtures/auth.ts` synthesizes the session
  cookie; `fixtures/stub-cloud.ts` stands in for Supabase. Audio *correctness* is
  not an E2E concern — that lives in `tests/unit/audio/` and `tests/integration/`.

See `tests/e2e/README.md` for the full architecture and debugging notes.

Four specs in that directory are local producers or diagnostics, not suite
members, and each self-skips unless its environment is set:
`backing-milestone-render.spec.ts` (the headless WAV producer for the
[backing listening protocol](backing-listening.md)), `backing-calibration.spec.ts`,
`record-omr-fixtures.spec.ts` (re-records the fused OMR fixtures; gated by
`RECORD_OMR_FIXTURES=1`) and `backing-render-audio.spec.ts` (needs real CDN samples).

## Deploy-script tests (`npm run test:deploy`)

`deploy/app/release.sh` runs on the production server, which makes it the one
piece of shell in the repo that can cause an outage. `deploy/app/release.test.sh`
is its regression suite — plain bash, no test framework — and CI runs it in the
`test` job right after vitest, on every branch.

It builds a throwaway `MANKUNKU_ROOT` under `mktemp -d` and puts stub `npm`,
`pm2`, `curl` and `node` binaries on `PATH`, so it runs anywhere without touching
a real server. Stub behaviour is driven by env knobs — `NPM_STUB_EXIT`,
`PM2_STUB_EXIT`, `CURL_STUB_DOWN`, `CURL_STUB_RELEASE`, `CURL_STUB_DELAY`,
`NODE_STUB_VERSION` — which is how a failed install, a stale-release health
response, or a Node upgrade get simulated.

Two things to know before you trust a local green run:

- `npm test` does **not** run it. It is a separate command.
- **4 of the 45 assertions skip on stock macOS**, because the deploy-lock tests
  need `flock` (util-linux). You get `skip - flock not available…` and 41
  assertions; Linux and CI run all 45.

What it pins: the immutable chunk pool (retention, eviction-before-hydration,
hardlink hydration, self-repair of a truncated chunk, stale-lock breaking), the
`current` swap and its refusal when `current` is a real directory, the
shared-`node_modules` cache key (install once, skip on an unchanged lockfile,
reinstall on a changed lockfile *or* a changed Node version, never record a
failed install as satisfied), failed-deploy stage cleanup **and its exception**
when `current` already points at the stage, the `/api/health` smoke check —
app down, wrong release id, and the budget being wall clock rather than
accumulated sleep — argument validation (a malformed release id or a missing
staged release is refused with `current` untouched), and release pruning (keeps
`KEEP_RELEASES`, spares the live release, ignores anything that isn't a
CI-generated release id).

## Backing-engine artifacts

The seeded backing generator is guarded by two **committed artifacts** rather
than hand-written expectations, so every engine change has to show its musical
diff in review:

| Artifact | Regenerate with | Fails via |
|---|---|---|
| `documentation/reference/backing-report.txt` | `npm run backing:report` | `tests/unit/audio/backing-report.test.ts` |
| `tests/fixtures/backing/golden-*.json` | `npm run backing:golden` | `tests/unit/audio/backing-golden.test.ts` |

Both scripts set an `UPDATE_*` env var and re-run the corresponding test in
write mode. Regenerate, **read the diff**, then commit it — a drifted artifact
that gets blindly refreshed defeats the entire mechanism. See
[Backing-track listening protocol](backing-listening.md) for the human half.

## What to Test

### Rules this suite follows

- **A test must be able to fail.** For every new test, name the source change that
  would turn it red — then make that change once and watch it happen. A test that
  survives the removal of the rule it names is not pinning anything (`expect(true)`,
  `toBeDefined()` on an import, or an assertion about what a mock was told to return).
- **Pins stay.** A test named after a date, an incident, a recorded take or a person
  is a regression pin; so is anything a comment says "pins". Never delete one as
  redundant, and never delete an `it.fails` expected failure — it documents an open
  problem and flips to passing when the problem is fixed.
- **Every diagnosed take joins the corpus.** When a real recording is mis-scored,
  its WAV (and its diagnostic JSON, kept for provenance) go to
  `tests/fixtures/recordings/` and a test in `tests/integration/pitch-replay.test.ts`
  scores it, as part of the fix.
- **Boundaries are separate tests.** `0.75` and `0.90` are different failure modes
  from `0.80`; a different key, instrument, session type or engine is not a duplicate.
- **Pin the environment the rule depends on.** A local-date test sets `process.env.TZ`
  to a zone on each side of Greenwich — CI runs in UTC, where local and UTC agree and
  a UTC-formatting regression would pass.
- **Cloud reads are tri-state.** Every synced store has a test that a *failed* cloud
  read throws or refuses to push, rather than merging against an empty set and
  overwriting another device's row (the 2026-07-13 incident class).
- **API routes have a verb contract.** `tests/unit/api/route-methods.test.ts` pins the
  exported methods of every `/api` route; SvelteKit answers 405 for any other verb.

### Where each kind of behaviour is tested

| Behaviour | Suite |
|---|---|
| Music theory, notation/ABC output, chord display, pickup bars | Vitest unit (goldens are byte-identical) |
| Pitch detection, segmentation, re-articulation tiers, bleed handling | Vitest unit + the recorded-take corpus (real WAVs replayed through the real detector in Node) |
| Scoring, fluency, grades, adaptive difficulty | Vitest unit |
| Lick-practice planning, rotation, tempo rules, reveal/passes | Vitest unit (the pure rotation and state modules) |
| Persistence, namespacing, cloud merge, outbox | Vitest unit + integration against `tests/helpers/cloud-sync-mocks.ts` |
| Importers (iReal, Band-in-a-Box, MuseScore, PDF, OMR) | Vitest unit + the lead-sheet corpus in `tests/fixtures/leadsheets/` |
| Svelte components, routes, navigation, hydration, storage isolation | Playwright |
| `release.sh` | the deploy suite |
| OMR parsing and validation | pytest |

### Not testable in Node

- **Svelte components** — they need a browser; use Playwright.
- **Live audio playback and Tone.js timing** — Node has no real `AudioContext`.
- **Live microphone input** — the detector itself *is* tested in Node, by replaying
  recorded WAVs through it; only the live capture path needs a browser.

## Tips

- Prove a new test can fail: break the rule it names, watch it go red, restore the source
- Keep tests focused: one behaviour per test
- Use descriptive test names that read as specifications
- Test edge cases: empty arrays, zero values, boundary conditions
- Use `toBeCloseTo()` for floating-point comparisons
- Don't test implementation details — test behavior and outputs
