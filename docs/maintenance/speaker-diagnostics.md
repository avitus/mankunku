# Production speaker diagnostics

The application writes one JSON line per received speaker check to its rotating PM2 output file. From the operator workstation, this command reads the last hour across current and rotated logs.

```sh
ssh mankunku 'find /home/deploy/.pm2/logs -type f -mmin -65 \( -name "mankunku-out-*.log" -o -name "mankunku-out-*.log.gz" \) -exec zgrep -hF "\"event\":\"speaker-check\"" {} +' |
  jq -c 'select(.event == "speaker-check" and ((.at | sub("\\.[0-9]+Z$"; "Z") | fromdateiso8601) >= (now - 3600))) |
    {at,version,clientVersion,surface,session,cueNumber,attempt,graphLeadSeconds,learnedCuesAtStart,closingStartSeconds,retryStage,retryFailure,retryOffsetDeltaSamples,retryReduction,retryTransientReduction,retryValidationGain,stage,result,method,reduction,transientReduction,initialFailure}'
```

Group by server version, client version, surface, anonymous session and cue number. A second capture shares its cue number. A nonzero `closingStartSeconds` identifies a check that also tried a later section of the same recording. An active result on that row passed verification on both the ending and the opening. Count a cue as active if either attempt verified. `calibrated-gain` means that the original calibration level passed after the level fitted on the opening of the cue failed. The other methods are saved calibration, a correction fitted on this cue, or a response learned from earlier verified cues. Reduction and transient reduction are measured in dB during Listen. Use the Settings and practice outcomes to distinguish a missing profile, a rejected sound check, and device changes. The diagnostic-probe result identifies operator delivery checks.

For startup comparisons, group attempts by session and cue, then compare cue 1 with later cues on the same surface and client version. `graphLeadSeconds` measures audio-clock seconds from verifier readiness to the scheduled Listen start. A negative value means Listen was scheduled to start before the verifier was ready. `learnedCuesAtStart` counts observations in the learned response available when the cue was scheduled.

For a closing retry, `retryStage` identifies insufficient samples, failed validation on the ending or opening, disagreement on timing, or excessive correction power. A successful retry reports `verified`. For opening and ending rejections, `retryFailure`, `retryReduction`, `retryTransientReduction` and `retryValidationGain` describe that window. `retryOffsetDeltaSamples` is the closing estimate minus the full-capture estimate when both exist. Clients released before these fields omit them.

Delivery is best effort and capped at 60 events per minute per network address and 300 total per server process. The measurements are anonymous client reports and provide an advisory view of rollout health. Recordings, phrase names and account identifiers stay out of this feed. Use the optional local recording export when investigating an individual note. After a timeout, the local export can include the completed Listen clip if the same capture permission was active from measurement start through the journal write and storage succeeded. The journal keeps the latest 64 checks. A timeout has no reduction measurement because verification missed the scoring deadline. Account deletion also attempts to clear the speaker journal from the current browser. If local cleanup fails, Settings asks the user to remove Mankunku’s site data in the browser. Browser site-data removal also works after a rollback. Delete any previously downloaded reports separately.
